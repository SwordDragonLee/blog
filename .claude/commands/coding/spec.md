# /spec - 生成功能规范

## 使用方式

```
/spec RAG 问答要支持单篇文章内问答，答案只来自这篇文章
```

## 执行步骤

1. 分析用户需求，明确功能范围与「不做什么」（明确排除项）
2. 读取相关代码现状：
   - 根据需求描述定位涉及的存量模块（service、api、页面、组件）
   - 读取这些文件，了解现有数据结构、接口契约与组件复用情况
3. 向用户确认工作模式：
   - [1] 先讨论再出文档（推荐，需求复杂时使用）：AI 基于代码现状一次性列出需要澄清的关键问题，达成共识后再生成
   - [2] 直接生成文档：基于现有信息直接输出，后续再修改
4. 如果用户选择「先讨论再出文档」：
   - 按照「讨论问题模板」一次性列出所有需要澄清的问题
   - 用户回答后，进入步骤 5
5. 如果用户选择「直接生成文档」，跳到步骤 6
6. 确定文档名两要素（无法确定 slug 时主动询问）：
   - `{YYYY-MM-DD}`：当天日期
   - `{slug}`：英文 kebab-case 简述（如 `rag-single-article-qa`）
7. 生成设计文档，包含：
   - 背景与目标（价值、与现有架构的衔接点）
   - 关键决策表（决策点 | 选择 | 理由）——多方案取舍必须在此留痕
   - 数据流 / 接口契约（路径、方法、请求响应结构；前台新接口只能挂 `/portal/*` 只读组）
   - 数据模型（新表 / 字段，GORM AutoMigrate 影响）
   - 配置项（config.yaml 新增项 + .env 环境变量，遵守「三处同步」）
   - 边界情况与失败路径（取消、重试、幂等、依赖缺失降级）
   - 验证方式与回滚思路

## 输出

将设计文档写入 `docs/superpowers/specs/{YYYY-MM-DD}-{slug}-design.md`。格式对齐既有样例：无 YAML frontmatter，头部为 `# {标题} 设计文档` + `日期:` + `状态:` 行。

## 约束

- 必须符合 `.claude/specs/` 全部规范，红线以 `specs/common/project-constraints.spec.md` 为准
- 文档中不得出现明文密钥，密钥相关只写「从 .env 读取」
- 复用优先：先查 `llm/`、`qdrant/`、`mq/` 等现有封装与 admin/blog 现有组件，不重复造轮子

## 讨论问题模板

进入讨论模式时，AI 基于代码现状一次性列出问题，只列与当前需求相关的维度。提问末尾注明「你可以逐条回答，也可以只回答有异议的，其余我按默认处理」。

### 功能边界
- 涉及哪些端/模块（server、admin、blog）？是新增还是改造存量？
- 不做什么？

### 数据与接口
- 涉及哪些接口？已有还是需要新建？
- 关键字段的含义、枚举值、格式要求？
- 新表还是扩展现有表？

### 交互与展示
- admin 列表是否需要分页、筛选？表单有哪些校验？
- blog 前台是否公开（/portal）？SEO / ISR 是否受影响？

### 复用判断
- 现有 service / llm / qdrant 封装是否有可复用的？
- admin / blog 现有组件中是否有可复用的？

### 约束条件
- 是否涉及状态机变更（draft ⇄ published）、缓存失效、MQ 消息？
- 模型成本（主模型套餐额度 vs 免费档）是否需要评估？
