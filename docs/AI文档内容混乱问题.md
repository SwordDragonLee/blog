# RAG 案例复盘：短查询导致检索污染（回答串台）

> 场景：博客前台技术问答里问「深入 fiber」，回答的 Fiber 部分正常（引用 React 文章），
> 却额外出现整章 gin-vue-admin 内容，还有一句强行搭桥的
> 「Fiber 可以类比为 gin-vue-admin 中的初始化器模式」。
> 本文按「现象 → 定位 → 根因 → 方案与权衡 → 面试表达」复盘，所有数据来自真实复现。

## 一、现象

用户提问「深入 fiber」，问答模型的回答结构：

- Fiber 的定义、可中断渲染 —— 引用 [1]（React 文章片段，**正常**）
- 「Fiber 在 gin-vue-admin 中的应用」整节 + 「Fiber 类比为初始化器模式」—— 引用 [2][4]（gva 文章片段，**串台**）

关键推断：**引用编号只可能来自检索阶段返回的片段**，生成模型不会凭空造出「gin-vue-admin」这个词——所以污染发生在检索层，不是生成层。

## 二、定位过程

1. **确认知识库内容**：Qdrant scroll 列出已索引文章，库里同时存在 react（2 篇）、gin-vue-admin（4 篇）、vue-core（2 篇）、langchain（1 篇）共 9 篇文章。
2. **写复现脚本**（`rag-debug.js`，仓库根目录）：用与后端完全相同的配置——同一个 embedding 模型（SiliconFlow bge-m3）、同一个 Qdrant 集合——对任意问题执行检索，**不带阈值过滤**，输出完整得分分布。
3. **对照实验**：同一问题，短问法 vs 完整问法。

## 三、根因链（三连击）

1. **短查询让向量空间「变平」**。「深入 fiber」五个字的查询向量，与库里所有中文技术文章的相似度落在 0.4387~0.4693 之间——**极差仅 0.03**。中文技术文章词表高度重叠（架构/组件/渲染/框架/初始化），bge-m3 这类双塔 embedding 对短查询几乎没有区分度。换成完整问题，分数立刻拉开（0.72 vs 0.54）。
2. **阈值 0.3 形同虚设**。全部命中 ≥ 0.43，一个也拦不住。阈值是兜底工具，不是精度工具。
3. **LLM 不会拒绝素材，只会硬圆**。两块 gva「初始化器/分层架构」片段进了上下文，system prompt 又要求「仅依据片段回答」——它不能不答 Fiber，也甩不掉 gva 片段，于是编出「类比初始化器」这座桥。**给什么素材就圆什么故事，是 LLM 的本性，prompt 写得再严格也拦不住**。

补充：本文的知识库还有「按文章分组引用」的机制（同一文章多块合并、引用一篇一条），它解决的是引用展示重复问题，与本案的检索污染正交——top_k=5 混进 2 篇无关文章，分组后依然混进 2 篇。

## 四、解决方案与权衡

| 方案 | 做法 | 效果 | 代价 |
|---|---|---|---|
| **A. 调高阈值** | `score_threshold` 0.3 → 0.45 | 只能滤掉尾部（0.4387~0.4493），**0.4552 的 gva 依然漏网**——平坦分布里切不干净 | 一行配置 |
| **B. 检索前 query 改写（推荐根治）** | 检索前用 glm-4-flash（免费档）把「最近几轮对话 + 本轮问题」改写成一句独立完整的问题，再拿去向量化 | 根治短查询问题；顺带解决多轮指代（先聊 React 再问「它的调度器呢」，现在原始 query 检索不到） | 每轮多一次免费模型调用（几百 ms，问答本就走 SSE 流式，无感）；需处理改写失败时降级用原始 query |
| **C. 混合检索** | 向量 + BM25 关键词检索，RRF 融合排序 | 「fiber」这类英文专有名词是强关键词，BM25 字面精确命中 React 文章，专治专有名词查询 | 需要关键词索引与融合逻辑；当前语料仅 9 篇 23 块，规模上去后再加 |
| **D. Rerank 精排** | 候选块用 cross-encoder（如 bge-reranker-v2-m3）对 query-doc 交叉编码重排 | 双塔向量是「各自编码再比对」，cross-encoder 让 query 和文档互相看见，短查询区分度显著更好 | 每个候选块一次推理，增加延迟与依赖 |

**落地顺序建议**：先 A（兜底更紧），主力做 B（性价比最高的一刀），语料与流量上来后补 C/D。

**通用教训（本案最有迁移价值的两句话）**：

- **检索是 RAG 的天花板，生成只是忠实执行**——检索塞进来的垃圾，模型会包装成答案。
- **LLM 不能当过滤器用**——它没有「拒答无关素材」的机制，治污染必须在检索层解决。

## 五、面试怎么讲

### 30 秒版本

> 我在自己项目的 RAG 问答里遇到一个串台问题：问 React Fiber，回答里混进了另一个项目的内容。定位发现根因在检索层——用户问题只有五个字，embedding 把库里所有中文技术文章的相似度压得几乎一样平（0.44 到 0.47），我设的 0.3 阈值拦不住任何东西，top5 里混进两块无关片段；而 LLM 不会拒绝素材，只会把给到的片段硬圆进答案，编出「Fiber 类比初始化器」这种强行搭桥。我写了一个和后端同配置的复现脚本，做短查询/完整查询的对照实验证实了这一点。方案上我评估了四层：调阈值只能缓解，根治是检索前用免费小模型把对话历史加问题改写成完整 query，再往后是 BM25 混合检索和 cross-encoder 精排。

### 展开时的加分点

- 主动给出**复现数据**（上面两张得分表）——「我不是猜的，是跑出来的」
- 强调定位手法：先从**引用编号必然来自检索结果**反推污染在检索层，缩小排查面
- 顺势带出整个 RAG 设计的其他决策：无命中短路不调 LLM、按文章分组引用、embedding 与问答模型分档（免费模型面向公众）

### 可能的追问与接法

**Q：为什么不直接把 top_k 调小？**
A：复现数据里 gva 片段排第 3，top3 照样混。top_k 控制召回量，解决不了排序质量。

**Q：阈值 0.45 是怎么定的？**
A：本例的教训恰恰是阈值只能在分数带可分时起作用。定法是抽样问题看命中分布，找相关/不相关两个分数带的分界；当分布平坦（如短查询）时无带可切，所以根治不在这里，阈值只做兜底。

**Q：为什么不用 BM25 / 混合检索？**
A：「fiber」是英文强关键词，BM25 会字面精确命中 React 文章，向量+BM25+RRF 是生产标准组合。当前语料只有 9 篇文章 23 个块，复杂度配不上规模，语料扩大后第一个加它。

**Q：query 改写用什么模型？加多少延迟？**
A：问答对话模型本来就是单独配的免费档（glm-4-flash），改写复用它，多一次调用几百毫秒；问答本身是 SSE 流式，总时长以秒计，无感。要点是改写失败要降级回原始 query，不能因为改写挂掉而拒答。

**Q：还知道哪些相关方法？**
A：HyDE——让模型先生成一段假设性答案、拿答案向量去检索，适合查询与文档措辞差异大的场景；multi-query——一个问题改写成多个检索视角合并去重；rerank——cross-encoder 精排。按实现成本排：改写 < 混合检索 < rerank < HyDE。

**Q：这个问题暴露了 RAG 的什么本质？**
A：两条——检索决定上限，生成只是忠实执行；LLM 没有审查素材的能力，prompt 拦不住污染，必须在检索层动手。
