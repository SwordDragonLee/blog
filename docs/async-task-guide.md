# 异步任务机制解读（写给要读懂这份代码的你）

> 这份文档解释「提交一个 Git 仓库地址 → 自动生成 4 篇文章」这条异步链路的每一步。
> 读完后你应该能回答：任务在哪里排队？谁在执行？失败了会怎样？进度从哪来？为什么不会丢、不会乱？

---

## 0. 先用一分钟看懂全局

整个系统只有一句核心约定：

> **数据库的 `gen_task` 行是「事实」，RabbitMQ 里的消息只是「通知」。**
> 消息里只带一个任务编号，不含任何业务数据；执行者拿到编号后自己回数据库查最新状态。

```
你在管理台点「创建任务」
        │
        ▼
┌──────────────────────────────┐
│ ① TaskService.Create         │  往 MySQL 写一行 gen_task（pending）
│    (service/task.go)         │  往 RabbitMQ 发一条消息 {"task_id":7}
└──────────────┬───────────────┘
               │  消息静静躺在队列里
               ▼
┌──────────────────────────────┐
│ ② Consumer（消费者）          │  同一个 Go 进程里的后台 goroutine
│    (mq/consumer.go)          │  从队列取消息 → 拿着 7 去执行
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ ③ Pipeline（流水线）          │  真正干活的：克隆→分析→LLM→写文章→配图→入库
│    (task/pipeline.go)        │  每前进一步就往 Redis 写一次进度
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│ ④ 管理台每 2 秒轮询           │  GET /tasks/7 → 后端合并 DB + Redis → 进度条动了
│    (web/admin TaskStore)     │
└──────────────────────────────┘
```

为什么叫「异步」？因为 ① 瞬间就返回了（网页立刻显示「排队中」），而 ③ 要跑几分钟。
中间靠队列把「接收请求」和「干活」解耦——HTTP 服务永远不会被慢任务拖住。

## 1. 出场的角色（先认清谁是谁）

| 角色 | 代码位置 | 一句话职责 |
|---|---|---|
| **任务行** `gen_task` | `model/gen_task.go` | 任务的事实档案：状态、进度、报错、git 地址。唯一权威 |
| **消息** `{"task_id":7}` | `mq/mq.go:31` | 一张「7 号该干活了」的纸条。丢了可以补，重复了不怕（后面讲为什么） |
| **Publisher** | `mq/publisher.go` | 发纸条的人。30 行 |
| **Consumer** | `mq/consumer.go` | 取纸条、安排执行、根据结果 ack/nack 的调度员 |
| **Pipeline** | `task/pipeline.go` | 干活的人。六个阶段串行执行 |
| **progressReporter** | `task/progress.go` | 干活时往 Redis 写进度条和日志的记录员 |
| **死信队列 (DLQ)** | RabbitMQ 里的 `blog.task.dlq` | 反复失败的「废纸篓」，进来的任务会被标记 failed |
| **Redis** | 两个 key | `task:7:progress` 进度快照；`task:7:logs` 执行日志 |

## 2. 一个任务的完整一生

### 阶段 A：出生（service/task.go 的 `Create`）

```go
① INSERT INTO gen_task ... (status=pending)   // 先落库
② PublishTask(t.ID)                           // 再发消息
③ 成功后写 queued_at = 现在                    // 标记「已进队」
```

**顺序为什么是先库后队？** 数据库是事实，消息只是通知。先让事实存在，再喊人。
如果反过来，消费者可能拿着消息来查库，发现行还不存在，按「任务已删除」直接丢弃。
两步之间如果进程崩溃，会留下「有行、没消息」的孤儿任务——靠第 5 节的补偿机制捞回。

### 阶段 B：排队（RabbitMQ 里发生了什么）

- 消息躺在队列 `blog.task.generate`，**持久化**的（broker 重启也不丢）
- Consumer 有 N 个 worker（配置 `task.concurrency`，默认 1），每个 worker 一次只领 1 条消息
  （`ch.Qos(1)`——防止 broker 把几百条消息一股脑塞进内存）

### 阶段 C：执行（task/pipeline.go 的 `Handle`）

拿到 task_id 后，流水线开始六步走，每步都会 `prog.step(百分比, 步骤名, 说明)`：

| 步骤 | 进度 | 干什么 |
|---|---|---|
| ① 克隆仓库 | 5% | `git clone --depth 1` 到临时目录，结束自动清理 |
| ② 仓库分析 | 15% | 识别语言/技术栈，挑出最值得看的代码文件 |
| ③ LLM 分析 | 30% | 把仓库摘要喂给大模型，得到技术栈总结 + 4 篇文章的选题大纲 |
| ④ 逐篇写作 | 30→90% | 每篇文章调一次 LLM，输出 JSON（标题/正文/标签/配图数据） |
| ⑤ 渲染配图 | — | LLM 只给图表数据，Go 代码确定性地画成 SVG，保证 100% 成功 |
| ⑥ 入库 | 100% | 4 篇文章存为 draft，任务标 success |

### 阶段 D：汇报进度（task/progress.go）

每次 `step()` 做两件小事：

- 覆盖写 Redis hash `task:7:progress`（就 4 个字段：步骤名/百分比/说明/时间）
- 往 Redis list `task:7:logs` 追加一行日志（最多留 200 条）

**为什么进度放 Redis 不放 MySQL？** 进度是高频、易失的临时数据——任务结束后没人
在乎中间过程，7 天自动过期。终态（成功/失败）才进 MySQL 作为永久记录。

## 3. 出错之后会怎样（最重要的部分）

消费者拿到执行结果后，只有四种可能，每种的处理写在 `mq/consumer.go` 的
`handleDelivery` 里：

| 结果 | 消费者动作 | 消息的下场 | 任务的结局 |
|---|---|---|---|
| ✅ 成功 | **ack**（确认） | 从队列消失 | success，文章入库 |
| 🛑 服务停机 | **nack + 重新入队** | 回队列，重启后重投 | 停机不背锅，重启后接着跑 |
| 🚫 被手动取消 | **ack 丢弃** | 从队列消失 | canceled（接口已落库） |
| ❌ 真失败 | **重投**，最多 3 次 | 带 `x-retry-count+1` 重回队列 | 3 次后进死信队列 + 标 failed |

几个关键细节：

- **停机和失败是两回事**：停机（ctx 取消）不写失败状态，消息重投等重启；只有业务真出错才走失败分支（`pipeline.go` 的 `fail()`）
- **重试计数存在消息头里**，跟着消息走，不用查历史
- **3 次重试是立即的**（没有退避等待），对「git 地址写错」这种必败任务，几秒内就烧完进死信
- 进死信前会回调 `OnDead`（`main.go`）：把任务标 failed、往 Redis 写「失败」进度，管理台立刻可见

## 4. 为什么消息丢了会重复、任务也不会乱（幂等）

消息语义是 **at-least-once（至少一次）**：broker 只保证「不丢」，不保证「不重」。
崩溃重启后，同一条消息可能被执行第二次。所以流水线必须做到——

> **同一任务跑 10 次，数据库的结果和跑 1 次一样**（顶多多花几次 LLM 的钱）

四个具体手段（都在 `task/pipeline.go`）：

1. **入口检查**：任务已被删除/取消 → 消息直接丢弃，不执行
2. **跑前清场**：`cleanupPreviousDrafts` 先删掉本任务上次跑出来的草稿文章（已发布的不动），防止新旧混杂
3. **文章按 slug 覆盖**：查到同名文章就覆盖内容，不是再插一行
4. **配图整篇重建**：先删该文章全部旧配图，再全部重画

## 5. 孤儿任务与补偿（service/task.go 的 `RecoverUnqueued`）

「先落库、后发消息」两步之间如果崩溃，会留下**孤儿任务**：
数据库里有行 pending，但消息从未发出——没有任何机制会执行它。

识别方法：加了 `queued_at` 列。投递成功才写时间戳；**`queued_at IS NULL` 的 pending
任务 = 孤儿**（如果是投递报错，任务会被标成 failed，不会是 NULL+pending）。

补救方法：进程**每次启动时**扫一遍孤儿任务，把消息补发进队列。因为孤儿消息必然
不存在（这正是孤儿的定义），补发不会造成重复执行。

## 6. 取消和删除是怎么生效的

任务可能处于两种状态，取消的方式不同（`service/task.go` 的 `Cancel`）：

- **还在排队**（消息没被消费）：把 DB 状态改成 canceled。消息迟早会被消费到，
  流水线入口一查状态不对，直接丢弃
- **正在执行**（LLM 调用跑到一半）：除了改状态，还通过 `CancelTask` 取消它的
  context——流水线里每个耗时操作都盯着 context，收到取消信号立即中断退出

消费者用一张注册表（`cancels map[任务ID]cancel函数`）记住「当前正在跑哪些任务」，
这就是为什么运行中的任务能被秒杀。

## 7. 进度是怎么显示到管理台的

```
Pipeline 每步 ──写──▶ Redis task:7:progress
                              ▲
管理台每 2 秒 ──GET /tasks/7──┤ 后端：读 DB（终态） + 读 Redis（实时进度）合并返回
                              ▼
                        进度条 + 日志滚动
```

- 后端规则：任务**进行中**以 Redis 为准（实时），任务**已结束**以 DB 为准（权威）
- 前端拿到新值后做 diff，只有步骤名变了才往日志面板追加一行，避免刷屏

## 8. 监控指标（GET /metrics）

| 指标 | 含义 | 什么时候看 |
|---|---|---|
| `blog_mq_connect_total` | 连上 RabbitMQ 的次数 | 疯狂增长 = 网络不稳 |
| `blog_mq_publish_total{result}` | 投递成功/失败 | error 增长 = MQ 有问题 |
| `blog_mq_consumed_total{result}` | 消费终局：ack/requeue/discard/retry/dead | retry、dead 增长 = 任务在失败 |
| `blog_mq_consume_duration_seconds` | 单条消息处理耗时 | 生成任务分钟级属正常 |
| `blog_mq_inflight` | 正在处理的消息数 | 恒等于并发中的任务数 |

## 9. 出问题了怎么排查（速查表）

| 现象 | 先看哪里 | 通常的原因 |
|---|---|---|
| 任务一直 pending 不动 | `GET /metrics` 看 inflight；看 RabbitMQ 管理台队列 | 有任务在占着 worker（并发=1 要排队）；MQ 挂了 |
| 任务 failed，error 是「任务多次重试仍失败」 | 日志里的具体报错 | LLM/git 克隆等连续失败 3 次，消息在死信队列里 |
| 任务 failed，「投递任务消息失败」 | RabbitMQ 是否存活 | 创建时 MQ 不可用，点「重试」即可 |
| 进度百分比不动但状态是 running | Redis `task:7:progress` 的 updated_at | 大模型正在长时间生成（单次可到几分钟），属正常 |
| 重启后任务自动开始跑了 | 正常现象 | 两种可能：停机时消息被 nack 重入队（续跑）；或孤儿任务被启动扫描补投 |
